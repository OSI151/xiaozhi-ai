## 一、总体结构

### 1.1 决策：新建板卡目录，不改官方板卡

有三个选项，选第三个。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 直接改 `boards/bread-compact-wifi/` | 最简单，默认板卡就是它 | 污染官方文件，以后跟官方对比全乱，官方升级无法干净合并 |
| B | 复制 `qebabe-xiaoche/` 到 2.2.4 | 电机代码原地不动 | qebabe 是 2.1.0 时代的板卡，跟 2.2.4 的 `board.h` 接口可能对不上 |
| **C** | **新建 `boards/[BOARD_NAME]/`，从 `bread-compact-wifi` 复制起步** | **官方文件一行不动，本地硬件集中一处，随时能切回官方板卡调试** | **要改 `Kconfig.projbuild` 和 `CMakeLists.txt` 各加一项** |

选 C 的核心理由：这份固件以后还要跟官方 2.2.4 甚至 2.5.2 同步。官方文件越干净，同步成本越低。多加一个 Kconfig 条目的代价，远小于每次合并都要人工分辨"这行是官方改的还是本地改的"。

目录建议名：`main/boards/deepseeking-robot/`（名字可换）。

文件构成（跟官方板卡保持同构，就三个文件）：

```
main/boards/deepseeking-robot/
├── config.h                    # 全部引脚、开关、常量
├── config.json                 # 板卡元信息（2.2.4 新引入）
└── deepseeking_robot.cc        # Board 子类：初始化 + MCP 工具注册
```

**注册一个板卡要改三处**（这是选 C 方案的全部代价）：

1. `main/Kconfig.projbuild` 的 `choice BOARD_TYPE` 里加一条：
   ```kconfig
   config BOARD_TYPE_DEEPSEEKING_ROBOT
       bool "DeepSeeking Robot (桌面机器人)"
       depends on IDF_TARGET_ESP32S3
   ```
2. `main/CMakeLists.txt` 的 `if(CONFIG_BOARD_TYPE_...)` 链里加一个 `elseif`：
   ```cmake
   elseif(CONFIG_BOARD_TYPE_DEEPSEEKING_ROBOT)
       set(BOARD_TYPE "deepseeking-robot")
   ```
3. 建目录，放 `config.h` / `config.json` / `.cc`

**顺带确认一件事**：`board.h` 在 2.1.0 和 2.2.4 之间**逐行完全一致**（`diff` 零差异）。所以 B 方案（直接复制 `qebabe-xiaoche/`）在接口层面也是能编译的——选 C 不是因为 B 有硬伤，纯粹为了官方文件保持干净。

板卡基类的 8 个纯虚方法（`GetBoardType` / `GetAudioCodec` / `GetNetwork` / `StartNetwork` / `GetNetworkStateIcon` / `SetPowerSaveLevel` / `GetBoardJson` / `GetDeviceStatusJson`）都由 `WifiBoard` 实现好了，新板卡只要继承 `WifiBoard` 就不用管这些。

### 1.2 分层

```
┌─────────────────────────────────────────┐
│  服务层  MCP 工具 / HTTP 路由 / 语音协议  │
├─────────────────────────────────────────┤
│  控制层  Application 电机中枢 / 状态联动  │
├─────────────────────────────────────────┤
│  驱动层  VL6180X / WS2812 / RoboEyes     │
├─────────────────────────────────────────┤
│  硬件层  板卡目录（引脚、I2C 总线、初始化）│
└─────────────────────────────────────────┘
```

**约束：驱动层不认识 Application。** 驱动只暴露「设置颜色」「读距离」这种原子操作，回调通过 `std::function` 或者 `extern "C"` 转发函数实现，跟 2.1.0 现有的 `HandleMotorActionForApplication` 一个路子。

### 1.3 模块依赖顺序

```
电机 ──┬─→ 情绪微动作（依赖电机）
       └─→ 巡逻/跟随（依赖电机 + 测距）

WS2812 ─→ 状态灯效（依赖语音状态，独立）

动画 ──→ 无依赖（只碰显示层）

Web ───→ 依赖电机（摇杆）+ 灯效（gcode）+ 配置（NVS）
```

真正的前置依赖只有两条：**电机是巡逻/跟随的前置**，**电机和灯效是 Web 的前置**。

## 二、七个模块的契约

| 模块 | 输入 | 输出 | 失败时怎么办 |
|---|---|---|---|
| 电机 | 方向 0-4、速度 0-100、时长 ms、优先级 | 四路 PWM 占空比 | `InitMotorPwm` 失败 → 回退 GPIO 开关（2.1.0 已有这段） |
| WS2812 | gcode 字符串 | 灯带像素 | 初始化失败 → 6 个工具统一返回 `"LED not available"` |
| VL6180X | 无（主动轮询） | 距离 mm + 状态 | `MODEL_ID != 0xB4` → 置 `available_=false`，4 个 robot 工具返回 `"requires distance sensor"` |
| RoboEyes | 表情名 | 直接刷 panel | `Begin()` 失败 → `reset()` + `lvgl_port_resume()`，退回静态图标（2.1.0 已有这段） |
| Web | HTTP 请求 | JSON | httpd 启动失败 → 只记日志，不影响语音 |
| MCP 工具 | 语音指令 | 文本 | 工具内部 try/catch 等价物，返回错误字符串 |
| 情绪联动 | 服务端 `emotion` 字段 | 电机动作 + 表情 | 未知 emotion → 记 warn，不动 |
| 场景管理 | 唤醒词 / BOOT 键 / MCP 调用 / idle 超时 | `scene_` 与 `robot_mode_` | 非法转移 → 记 warn 留在原场景（§3.6） |

**共同原则**：任何一个外设挂了，其余功能照常。测距模块找不到，语音对话和电机照样能用。

**场景管理是唯一的跨模块协调者**，它不直接碰硬件，只决定「现在该谁说了算」：屏幕归 LVGL 还是 RoboEyes、电机听模式的还是听语音反馈的、音效要不要静音。

## 三、九个必须先想清楚的摩擦点

### 3.1 `display.h` 是双向合并，不是单向覆盖

两版各有各的新增，谁都不能盖谁：

| 只有 2.2.4 有 | 只有 2.1.0 有 |
|---|---|
| `ClearChatMessages()` | `SetAnimatedEmotionMode(bool)` |
| `SetupUI()` | `IsAnimatedEmotionMode()` |
| `IsSetupUICalled()` | `SetEmotionDirection(int)` |
| `setup_ui_called_` 成员 | `UpdateAnimatedEmotion()` |
| | `animated_emotion_mode_` 成员 |

合起来是 12 + 4 = 16 个方法。**没有冲突，直接并**。

但要注意：2.2.4 的 `OledDisplay::SetupUI()` 是新增的 override（`SetupUI_128x64()` / `SetupUI_128x32()` 两个私有函数），2.1.0 的 `OledDisplay` 没有这个方法。合并 `oled_display.cc` 时这块要单独看，不能整文件覆盖。

### 3.2 两套表情系统，是分叉不是叠加

这是个容易想错的地方。

- **2.2.4 的表情** = FontAwesome 单字符图标，靠 `font_awesome_get_utf8(emotion)` 查表，画在 `emotion_label_` 这个 LVGL label 上
- **2.1.0 的眼睛** = RoboEyes 库直接刷 panel，**进去第一件事是 `lvgl_port_stop()` 把整个 LVGL 停掉**

所以它们互斥。2.1.0 的 `SetEmotion` 改成这样：

```cpp
if (animated_emotion_mode_) {
    roboeyes_adapter_->SetEmotion(emotion);   // 眼睛路径，LVGL 已停
} else {
    lv_label_set_text(emotion_label_, font_awesome_get_utf8(emotion));  // 图标路径
}
```

**推论**：眼睛模式下，状态栏、WiFi 图标、聊天字幕、时间全都不显示。这不是 bug，是原作者为了避开两个渲染器抢同一块 panel 故意做的。

**但「眼睛 + 字幕同屏」是做得到的，而且不用 canvas 桥接。** 查 2.2.4 的 `oled_display.cc:49-71`：

```c
.buffer_size   = static_cast<uint32_t>(width_ * height_),   // 8192 像素
.double_buffer = false,
.monochrome    = true,        // I1 格式 1 bit/像素 → 实际 buffer 仅 1024 字节
.full_refresh  = 0,           // ← LVGL 本来就走局部刷新
.direct_mode   = 0,
```

`full_refresh = 0` 意味着 LVGL **只对脏区调 `flush_cb`**，天生可以和 RoboEyes 共存。原作者之所以要 `lvgl_port_stop()`，是因为他把 RoboEyes 的画布设成了整屏 128×64，和 LVGL 的整个 screen 完全重叠，两个渲染器刷同一片显存必然花屏。

**把区域切开就行**：

| 区域 | 页 | 归属 |
|---|---|---|
| y = 0–47 | 0–5 | RoboEyes 独占 |
| y = 48–63 | 6–7 | LVGL 独占（字幕） |

`roboeyes_adapter_->Begin(content_left_, width(), 48, 30, panel_io_, panel_)` 后 RoboEyes 只刷前 6 页；LVGL 那边把 `chat_message_container_` 设成 `lv_obj_set_size(..., LV_HOR_RES, 16)` + `lv_obj_align(..., LV_ALIGN_BOTTOM_MID, 0, 0)`，只刷后 2 页。

**这样 `lvgl_port_stop/resume` 那一整套反复开关可以彻底不搬**——日志里它每隔 5 秒被调一次、`Panel task already running` 警告出现 12 次，全是空耗。

**有一个时序坑**：LVGL screen 背景是白色，第一次全屏渲染会把整块屏刷白。启动顺序必须是

1. LVGL 初始化 + `SetupUI()` + 首次全屏渲染（白屏）
2. 等首次 flush 完成
3. RoboEyes 接管 0–47，刷第一帧
4. 之后 LVGL 只刷 48–63

另外 `SetTheme()` 会触发全屏重绘，得在那个位置调一次 `roboeyes_adapter_->ForceRedraw()`（重置 `first_flush_`）。

**字号**：`main/CMakeLists.txt:81` 是 `set(BUILTIN_TEXT_FONT font_puhui_14_1)`，14px 普慧中文。128px 宽一行约 9 个汉字（原版的 `chat_message_label_` 宽 `width_ - 32 = 96px`，只有 6 个）。已经是 `LV_LABEL_LONG_SCROLL_CIRCULAR` 滚动，不换字体也够用。

### 3.3 MCP 工具注册要防重复

2.2.4 已经有的（`boards/common/lamp_controller.h` 注册的）：

```
self.lamp.get_state / turn_on / turn_off
```

这块跟 2.1.0 字节完全一样（1436 字节），**不用搬，2.2.4 自带**。

要新注册的（板卡目录里）：

```
self.motor.*        21 个（10 运动 + 11 情绪）
self.network.get_ip  1 个
self.rgb_led.*       6 个
self.robot.*         4 个
```

**检查点**：2.2.4 的 `mcp_server.cc` 里没有 `self.network.get_ip`，`AddUserOnlyTools()` 里也没有，所以这个工具要自己加，不会撞。

注册位置：板卡的 `InitializeTools()`，跟 qebabe 一样。

### 3.4 NVS 键空间要提前规划

三份配置各用一个命名空间，别混：

| 命名空间 | 键 | 来源 |
|---|---|---|
| `motor_config` | `forward_ms` `backward_ms` `left_turn_ms` `right_turn_ms` `spin_ms` `quick_fwd_ms` `quick_bwd_ms` `def_speed_pct` | 2.1.0 原样 |
| `led_config` | `led_count` `initial_gcode` `idle_gcode` `lightshow_gcode` `listening_gcode` `speaking_gcode` | 新写，参照 v206 实测 |
| `sensor_config` | 见 §3.5 | 新写，VL6180X 校准值 |

**理由**：v206 把灯效配置直接塞进 `motor_config`（从 `/api/config` 和 `/api/led/config` 是两个接口但共用存储推断），分不清边界。分开存以后好迁移。

### 3.5 测距参数全部运行时可改，不编译期写死

布局一变（换桌面、调角度、加高机架），`baseline` 就变。写死在代码里意味着每次都要重新烧录。所以全部塞 NVS，只存**不可推导的原始量**，派生量运行时算。

| 键 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `baseline_mm` | uint16 | 0（未校准） | 在平整桌面上静止时测到的斜距中位数 |
| `tol_pct` | uint8 | 15 | 容差百分比，派生 `safe_min = baseline*(100-tol)/100`、`safe_max = baseline*(100+tol)/100` |
| `scaling` | uint8 | 1 | 量程档位 1/2/3 → 200/400/600mm，对应私有寄存器 `0x097` = `0xFD`/`0x7F`/`0x54` |
| `near_mm` | uint16 | 50 | 障碍急停阈值（绝对距离，不是相对 baseline） |
| `far_mm` | uint16 | 100 | 迟滞外圈：靠近用 `near_mm`，离开用 `far_mm` |
| `edge_confirm` | uint8 | 3 | 连续几次无效读数才判桌沿 |
| `calib_ts` | uint32 | 0 | 校准时间戳（unix 秒），超过 7 天提示重校 |

**只存 7 个原始量，`safe_min_mm` / `safe_max_mm` 不存**——它们是 `baseline_mm × tol_pct` 的派生物，存了反而会出现"改了 baseline 忘了改 safe"的不一致。v206 就是存了三个值，日志里 `baseline=147 safe=127-167` 和 `Follow distances: retreat<44 normal=44-117 search>117` 两套阈值互相打架（baseline 147 落在 `search>117` 区间，静止时一直判"物体太远往前冲"）。这次让跟随阈值也从 `baseline` 派生，只保留一把尺子。

#### 校准怎么触发

四条路，随便哪条都行：

| 触发方式 | 用法 |
|---|---|
| **上电自动** | `baseline_mm == 0` 或 `calib_ts` 超过 7 天 → 启动时自动校一次 |
| **语音** | `self.sensor.calibrate`（MCP 工具，无参数） |
| **Web** | `POST /api/sensor/calibrate` |
| **按键** | 长按 BOOT 3 秒（不占用现有短按/长按语义，见 §3.3） |

#### 校准过程

1. 先停电机（`StopRealtimeMotorControl()`），等 200ms 让机身稳定
2. 采 20 次，间隔 50ms，总共约 1 秒
3. 丢掉 `range_status != OK` 和超量程的样本
4. 剩余样本取**中位数**（不是平均值，抗单点跳变）
5. 有效样本 < 10 → 判定失败，**保留旧值不写入**，返回错误
6. 成功则写 `baseline_mm` + `calib_ts`，返回完整结果

返回格式（MCP 与 Web 一致）：

```json
{"baseline_mm":147,"safe_min_mm":127,"safe_max_mm":167,"samples":20,"valid":18,"scaling":1}
```

**失败案例**：机器人在桌沿上校准、手挡在传感器前、桌面镜面反射过强——这三种都会让中位数失真。加一条保险：如果 20 个样本的极差超过 `baseline × 0.5`，判为"读数不稳定"，同样拒绝写入。

#### 为什么 `scaling` 也要可改

现在装的是 45° 斜向下、离地 10.4cm，斜距 `147mm`，1x 档量程 200mm 只剩 53mm 余量。这个余量能应付静止和慢速前进，但巡逻时如果机身俯仰几度，读数就可能冲出 200mm。

`scaling` 放运行时，可以在两种场景间切换：

- **静态/跟随**：1x 档，精度最高，量程够用
- **巡检/探索**：2x 档，量程 400mm，代价是误差翻倍（±5mm → ±10mm）

切档 = 重写 `0x096`/`0x097` 两个寄存器 + 重算 `baseline`（因为读数会变成原来的 2 倍）。所以切档后必须立刻重校，代码里把这两步绑成一个原子操作：`SetScaling(n)` 内部自动跟一次 `Calibrate()`。

### 3.6 场景管理：两态，加一个只在开机出现的官方界面

2.1.0 完全没有这个抽象——它只有 `DisplayMode` 两态（默认/眼睛），显示逻辑散在 `HandleStateChangedEvent` 里。v206 加进了机器人模式却没做场景管理，于是出了「robot 跑着跑着屏幕变成时钟、音效还在播」这种自相矛盾的状态。

#### 只有两态

```
   Sleep（大时钟）  ──短按 BOOT / 语音唤醒──▶  Eyes（眼睛 + 字幕）
        ▲                                              │
        └────────── 短按 BOOT / 闲置 60 秒 ─────────────┘
```

| 状态 | 屏幕 | 什么时候进 |
|---|---|---|
| `kDisplayModeSleep` | 整屏大字时钟 + WiFi 图标 | 开机激活完成、短按 BOOT、闲置 60 秒 |
| `kDisplayModeEyeOnly` | 眼睛动画 48 行 + 字幕 16 行 | 短按 BOOT、语音唤醒 |

#### 官方界面留着，但退出状态机

`SetStatus` 全仓 14 处调用，分布很干净：

| 位置 | 阶段 | 内容 |
|---|---|---|
| `application.cc:159/187/199/519/562/591` | **开机流程** | 正在配网 / 检测模块 / 检查版本 / 激活中 / 加载协议 |
| `:769/981/986/1019` | 运行时 | 待机 |
| `:1030/1039/1074` | 运行时 | 连接中 / 倾听 / 说话 |
| `:758`（`Alert()`） | 任意 | 报警文本 |

**前 6 处必须有地方显示**——开机那 9.6 秒屏幕上得写「正在激活」，这是用户唯一能看到的进度反馈。删了官方界面这段时间就是白屏。

**后 8 处已经没有信息增量**——待机/连接中/倾听/说话这四种状态，眼睛动画和字幕已经表达完了；`Alert()` 的报警走 `SetChatMessage`（`oled_display.cc:146` 直接写 `chat_message_label_`），落在字幕区，也不依赖官方界面。

所以官方界面**保留代码、退出状态机**，只在 `starting` / `activating` 阶段自动出现。

**枚举值怎么排**：

```cpp
enum DisplayMode {
    kDisplayModeDefault = 0,   // 开机阶段：状态文本。保持 0 不动
    kDisplayModeEyeOnly,       // 眼睛 + 字幕
    kDisplayModeSleep,         // 大时钟
};
```

`application.h` 里 `DisplayMode display_mode_ = kDisplayModeDefault;` 一个字都不用改，开机第一次渲染天然就是官方界面。若把 Sleep 设成 0，反而要在 `Initialize()` 里显式设回 Default，多一步且容易忘。

#### BOOT 键

| 当前 | 短按 | 长按 1 秒 |
|---|---|---|
| `Sleep` | → `Eyes` | 无 |
| `Eyes`（电机在动 / 正在播报） | 全停，留在 `Eyes` | → `Sleep` |
| `Eyes`（闲着） | → `Sleep` | 无 |

「全停」指两件事，顺序不能反：

```cpp
StopRealtimeMotorControl();          // ① 50ms 渐变断电，齿轮不冲击
AbortSpeaking(kAbortReasonNone);     // ② 切断 TTS
```

**长按留给「看一眼 IP」**：官方界面退役之后，IP 只在串口日志里，配网后要去控制台改提示词得知道 IP。长按显示官方界面 3 秒再自动回，正好把退役的界面利用起来。

**长按怎么实现**：`Button` 构造第 3 参 `long_press_time` 现在是 0，改 1000；`OnLongPress` 用 `BUTTON_LONG_PRESS_START` 事件；`OnClick` 收到的是 `BUTTON_SINGLE_CLICK`，两者自动互斥，不用自己做计时器。

#### 睡眠：60 秒进时钟

**2.1.0 没有这个**。`grep -n "Timer" qebabe-xiaoche/compact_wifi_board.cc` → 空，那块板卡从开机到断电都醒着。官方其他 8 个板卡的 `PowerSaveTimer(-1, 60, 300)` 只做 `esp_pm_configure` 降频 + 关麦克风 + 300 秒关机，**屏幕一根线都不动**；`SleepTimer` 直接 `esp_light_sleep_start()` 停 CPU，WakeNet 也跟着停，喊不醒。

两个现成类都不合用，自己写一个：

```cpp
esp_timer_handle_t idle_timer_ = nullptr;
static constexpr int kIdleToClockSeconds = 60;

void Application::ResetIdleTimer() {
    if (idle_timer_ == nullptr) return;
    esp_timer_stop(idle_timer_);
    esp_timer_start_once(idle_timer_, kIdleToClockSeconds * 1000000ULL);
}
```

回调里只有一个检查点：

```cpp
if (!self->CanEnterSleepMode()) return;    // robot 模式下直接返回
self->EnterClockScene();
```

`EnterClockScene()` 四件事：

```cpp
display->SetAnimatedEmotionMode(false);                 // 眼睛让位
display->ShowClock();                                   // 画大字时钟
board.SetPowerSaveLevel(PowerSaveLevel::LOW_POWER);     // 80MHz，WakeNet 照跑
display_mode_ = kDisplayModeSleep;
```

**不调 `esp_light_sleep_start()`**，只降频不真睡。麦克风得一直听着，喊「你好小智」得能喊醒。

`ResetIdleTimer()` 五个调用点，**漏一个就会出现「说着话突然变时钟」**：

1. 唤醒词触发
2. 开始说话（TTS 收到第一包）
3. 每次 MCP 工具执行完
4. 每次按键
5. 机器人模式退出

#### 修 v206 那个 bug

v206 的表现是「robot 模式跑一阵，屏幕变成时钟，但探索音效还在播」。根因在 `main/application.cc` 的 `CanEnterSleepMode()`：

```cpp
bool Application::CanEnterSleepMode() {
    if (GetDeviceState() != kDeviceStateIdle) return false;
    if (protocol_ && protocol_->IsAudioChannelOpened()) return false;
    if (!audio_service_.IsIdle()) return false;
    return true;
}
```

robot 模式运行时这三条**全部满足**（没在对话 / 通道关着 / 音效间隙音频空闲）→ 判定可以睡 → 切了显示，但模式任务照跑。

修复一行：

```cpp
if (robot_mode_ != kRobotNone) return false;
```

#### 全屏大字时钟也要自己写

2.1.0 唯一的时间显示是 `lvgl_display.cc:124-140`，往 **16px 高的状态栏**里塞 `HH:MM` 小字，跟 WiFi 图标抢位置。但一块占大半屏的大字时钟在原版源码里没有，是 v206 自研的。

**字体得先开**。`sdkconfig` 现状是 `CONFIG_LV_FONT_MONTSERRAT_14=y`，16 以上全关着：

```ini
# sdkconfig.defaults 加一行
CONFIG_LV_FONT_MONTSERRAT_40=y      # 全 ASCII 约 60–80KB flash，分区剩 1.4MB 够
```

```cpp
// 三个 label 用 flex 横排，冒号独立一个对象好单独调透明度
clock_row_ = lv_obj_create(screen);
lv_obj_remove_style_all(clock_row_);
lv_obj_set_size(clock_row_, LV_HOR_RES, 44);

clock_colon_ = lv_label_create(clock_row_);
clock_m_     = lv_label_create(clock_row_);
for (auto* l : {clock_h_, clock_colon_, clock_m_}) {
    lv_obj_set_style_text_font(l, &lv_font_montserrat_40, 0);
}
lv_label_set_text(clock_colon_, ":");

date_label_ = lv_label_create(screen);
lv_obj_set_style_text_font(date_label_, text_font, 0);      // 普慧 14
lv_obj_align(date_label_, LV_ALIGN_BOTTOM_MID, 0, -2);

void OledDisplay::ShowClock() {
    time_t now = time(nullptr);
    struct tm* tm = localtime(&now);

    if (tm->tm_year < 2025 - 1900) {                        // NTP 还没同步
        lv_label_set_text(clock_h_, "--");
        lv_label_set_text(clock_m_, "--");
        lv_obj_set_style_text_opa(clock_colon_, LV_OPA_COVER, 0);   // 无效时间冒号常亮
        lv_label_set_text(date_label_, "");
        return;
    }

    char h[4], m[4], d[32];
    snprintf(h, sizeof(h), "%02d", tm->tm_hour);
    snprintf(m, sizeof(m), "%02d", tm->tm_min);
    lv_label_set_text(clock_h_, h);
    lv_label_set_text(clock_m_, m);

    // 冒号每秒亮灭：奇数秒透明，偶数秒显示
    lv_obj_set_style_text_opa(clock_colon_, (tm->tm_sec & 1) ? LV_OPA_TRANSP : LV_OPA_COVER, 0);

    static const char* kWday[] = {"周日","周一","周二","周三","周四","周五","周六"};
    snprintf(d, sizeof(d), "%02d/%02d %s", tm->tm_mon + 1, tm->tm_mday, kWday[tm->tm_wday]);
    lv_label_set_text(date_label_, d);
}
```

**冒号用透明度而不是 `LV_OBJ_FLAG_HIDDEN`**：隐藏对象会退出 flex 布局，`20:40` 会瞬间挤成 `2040` 再弹回来，一秒抖两次。改透明度布局完全不动。

**重绘开销**：`lv_label_set_text` 传相同字符串时 LVGL 内部会比较，不触发重绘；每秒真正变化的只有冒号那个 label，约 12×40px ≈ 1 页。配合 §4.2 的脏区检测，这一秒只发 128 字节。

**日期用中文**（`11/07 周六`）：5 个 ASCII 约 35px + 空格 4px + 2 个汉字 28px ≈ 67px，128px 宽居中很宽松。

40px 下 `20:40` 约 110–120px，刚好塞满屏宽；40px 时钟 + 14px 日期 = 54px 高，垂直留 10px。

刷新**复用 `application.cc` 已有的 1 秒 `CLOCK_TICK` 事件**，不新起 timer。

#### 时间从哪来：一次 OTA 下发，之后靠内部 RC 走

**源码现状（2.2.4 实测）**：

```
grep -rn "sntp\|SNTP" main/          → 零命中，根本没启动 SNTP
main/ota.cc:191                      cJSON_GetObjectItem(server_time, "timestamp")
main/ota.cc:206                      settimeofday(&tv, NULL);
main/application.cc:331              CheckNewVersion();      ← 只在 ActivationTask() 里
```

时间来自 **OTA 接口返回的 `server_time.timestamp`**，跟固件版本号一起下发。`CheckNewVersion()` 只在开机联网后的 `ActivationTask()` 里调一次，**之后再也不调**。

每秒那个定时器只刷 UI，不碰网络：

```cpp
// application.cc:248
if (bits & MAIN_EVENT_CLOCK_TICK) {
    clock_ticks_++;
    display->UpdateStatusBar();      // 读本地 time()，纯内存
}
```

**问题在这**：

```
CONFIG_RTC_CLK_SRC_INT_RC=y                  ← 内部 RC 振荡器，没有外部 32.768kHz 晶振
CONFIG_ESP32S3_RTC_CLK_CAL_CYCLES=1024
```

内部 RC 校准后精度 **±1.5%**（datasheet，25°C），折算**每天漂约 20 分钟**。开机同步一次，到下午就差一截。

**加 SNTP**。lwip 的配置项本来就都在，只是没人启动：

```
CONFIG_LWIP_SNTP_MAX_SERVERS=1
CONFIG_LWIP_SNTP_UPDATE_DELAY=3600000        ← 1 小时
CONFIG_LWIP_SNTP_STARTUP_DELAY=y
CONFIG_LWIP_SNTP_MAXIMUM_STARTUP_DELAY=5000
```

```cpp
#include "esp_sntp.h"

void Application::StartSntp() {
    esp_sntp_setoperatingmode(ESP_SNTP_OPMODE_POLL);
    esp_sntp_setservername(0, "ntp.aliyun.com");
    esp_sntp_init();     // 立即同步一次，之后按 UPDATE_DELAY 每小时一次
}
```

挂在 `HandleNetworkConnectedEvent()` 里。开销是**每小时一个几十字节的 UDP 包**。

**必须先修的时区坑**。`ota.cc:200-206` 现在这么写：

```cpp
if (cJSON_IsNumber(timezone_offset)) {
    ts += (timezone_offset->valueint * 60 * 1000);   // 把 +480 分钟加进时间戳
}
tv.tv_sec = (time_t)(ts / 1000);                     // 存进去的已经是北京时间
settimeofday(&tv, NULL);
```

**它把本地时间当成 UTC 存了**。现在没设 TZ，`localtime()` 原样返回，所以显示是对的。但 SNTP 给的是真 UTC，两条路径一混，时间会突然差 8 小时。

统一改成走 TZ：

```cpp
// Application::Initialize() 里设一次
setenv("TZ", "CST-8", 1);      // POSIX 写法：CST-8 = UTC+8
tzset();
```

```cpp
// ota.cc:200 那段改成
tv.tv_sec = (time_t)(ts / 1000);      // 不再加 timezone_offset
tv.tv_usec = (suseconds_t)((long long)ts % 1000) * 1000;
settimeofday(&tv, NULL);
```

两条路径都往系统时间里写 UTC，`localtime()` 靠 TZ 转北京时间，不会打架。

**保底**：SNTP 首次同步可能失败（DNS 慢、网络刚连上）。`ShowClock()` 里已经有 `tm->tm_year < 2025 - 1900` 的判断，同步成功前显示 `--:--`，不会显示 1970 年的假时间。

### 3.7 机器人模式：四个子模式、两个工具

四个模式来自 v206 固件的 MCP 工具描述（二进制里挖出来的中文原文见 §4.4）。

| 模式 | 行为 | 需要传感器 |
|---|---|---|
| `explore` 探索 | 随机执行大动作（前进/后退/左右转/转圈），每个动作后随机等 1–3 秒 | 否 |
| `free` 自由 | 原地展示各种表情和情绪动作，每个动作后随机等 1–3 秒 | 否 |
| `follow` 跟随躲避 | >10cm 前进追、5–10cm 保持、<5cm 后退 | **是** |
| `edge_patrol` 边缘巡检 | 直行 → 判边缘 → 后退 → 转 90° → 继续 | **是** |

**接口做成两个独立工具，不用 toggle**：

```json
self.robot.start(mode)   // mode: explore / free / follow / edge_patrol
self.robot.stop()        // 无参数
```

v206 是 toggle 语义（再说一次「退出探索模式」就退出），但它的日志里有一次 LLM 拿到「退出探索模式」时没有对应工具、只能瞎猜。拆成两个明确的动作，`stop()` 能被「退出」「停下来」「别跑了」任意一种说法命中。

**`start()` 时传感器不可用直接拒绝**：`follow` 和 `edge_patrol` 本质靠距离驱动，没数据就是瞎跑。返回错误并说明，不启动。

#### 机器人模式下的语音交互

| 当前 | 事件 | 结果 |
|---|---|---|
| 机器人模式运行中 | 语音唤醒 / 说话 | 停该模式的音效 + 停大幅动作，进入对话；**模式不退出** |
| 机器人模式 + 说话中 | 短按 BOOT | 打断说话 + 停动作 + 清动作队列，**重新开始这个模式** |
| 机器人模式（没在说话） | 短按 BOOT | 退出模式 → 停所有动作 → 回 `Eyes` → 恢复睡眠计时 |
| 机器人模式 + 语音聊完 | — | **自动继续跑**，但先做一次原地动作（转圈或摆头）再进随机流程 |

「先做一次原地动作」是必要的保护：探索模式一个 `move_forward` 是 5 秒一米多，中途被唤醒、聊了 30 秒之后它已经不在原位了，直接接着跑可能撞墙或掉下桌沿。转个圈相当于重新校准它在哪。

**没有「挂起」这个状态**——上面三条规则已经把它吸收了。唤醒就是临时停手，BOOT 才是明确动作（重启模式或退出模式）。

**机器人模式期间不休眠**：`CanEnterSleepMode()` 里那一行 `if (robot_mode_ != kRobotNone) return false;` 就够，不用单独开关定时器。

### 3.8 安全闸门：传感器永远最高优先级

用户要的规则：**激光测距在机器人模式下优先级最高，任何动作都要先过它。**

做成「闸门」而不是「建议」，区别在于**拦截点放在电机命令的入口**——模式任务、语音反馈、Web 摇杆全走同一个口，谁也绕不过去。

#### 拦截点

`main/application.cc` 的 `SetRealtimeMotorCommand()` 是唯一的电机执行口（`:1331`，调用者只有 `HandleMotorActionWithDuration:1432`、`ExecuteMotorActionQueue:1485`、`HandleWebMotorControl:1619`）。函数签名加一个参数：

```cpp
void SetRealtimeMotorCommand(int direction, int speed, bool from_web = false);
```

只有 `HandleWebMotorControl` 传 `true`，另外两个用默认值。函数开头：

```cpp
const bool is_forward  = (direction == 4);
const bool is_backward = (direction == 2);

if (sensor_ok_) {
    // 传感器正常：不管谁发的，危险就拦
    if (is_forward && safety_block_forward_) {
        ESP_LOGW(TAG, "forward blocked (%s)", safety_reason_);
        return;
    }
    if (safety_speed_limit_pct_ < 100 && speed > safety_speed_limit_pct_) {
        speed = safety_speed_limit_pct_;
    }
} else if (!from_web) {
    // 传感器失效：遥控器豁免，其它路径限速限时
    if (speed > 50) speed = 50;
    if (is_forward || is_backward) {
        safety_deadline_ms_ = esp_timer_get_time() / 1000 + 1000;
    }
}
```

#### 三种情况

| 传感器状态 | 模式 / 语音 | Web 遥控器 |
|---|---|---|
| **正常** | 障碍 <50mm 停前进；桌沿 / 无读数停前进；50–80mm 限速 40% | **同样受保护**，撞墙也会停 |
| **无数据（坏了）** | 只能转向（左右转、转圈）；前后最多 1 秒、速度压到 50% | **完全豁免**，想怎么开怎么开 |
| **恢复数据** | 自动解除限制 | 恢复正常保护 |

传感器坏了还把遥控器锁死，连调试都做不了；传感器好的时候不限遥控器，一推摇杆就撞墙。两种情况必须分开。

#### 四个判定档位

| 档位 | 读数 | 动作 | 恢复条件 |
|---|---|---|---|
| **桌沿** | 读数无效 / 超量程 | 立即停车 + 禁前进 + 后退 150ms | 连续 3 次有效读数 |
| **障碍** | < 50mm | 立即停车 + 禁前进 | > 80mm（迟滞 30mm） |
| **近距警告** | 50–80mm | 限速到 40% | > 100mm |
| **正常** | > 80mm | 不干预 | — |

迟滞是必须的，不然在阈值附近会来回抖。

#### 1 秒硬限时怎么实现

不是靠调用者自己控制——模式任务可能传 5000ms，它不会听话。用一句截断：

```cpp
// HandleMotorActionWithDuration 起 motor_stop 定时任务时
if (!sensor_ok_ && (direction == 4 || direction == 2)) {
    deadline_ms = std::min(deadline_ms, 1000);
}
```

不管谁发的前进/后退，超过 1 秒都会被掐断。

#### 转向为什么可以无限

`direction == 1`（右）和 `3`（左）不触发任何限制。原地转圈不会撞墙也不会掉桌沿，放开。`spin_around` 用的是 `direction = 3, duration = 2000`，正好落在这条规则里。

#### 优先级排序

| 级 | 谁 | 怎么生效 |
|---|---|---|
| 最高 | **传感器闸门** | `SetRealtimeMotorCommand` 入口拦截，无例外 |
| 高 | BOOT 键 | 退出/打断模式，直接 `StopRealtimeMotorControl()` |
| 中 | 机器人模式 | 正常发动作，被拦就等 |
| 低 | 语音反馈微动作 | 前倾后仰，同样过闸门 |

传感器任务不能只「报告」，判桌沿时立刻 `StopRealtimeMotorControl()`，不等模式任务下一次发指令。

#### 状态标志

```cpp
std::atomic<bool> safety_block_forward_{false};
std::atomic<int>  safety_speed_limit_pct_{100};
const char*       safety_reason_ = "";
std::atomic<int64_t> safety_deadline_ms_{0};
std::atomic<bool> sensor_ok_{false};
```

### 3.9 传感器数据要随时可读

用户的原话：「传感器的数据必须随时能被读取到，包括让小智看到，就像看音量一样」。v206 的毛病是「偶尔读到，后来怎么也读不到」。

**根因**：`readRangeContinuous` 进去后一直等 `SYSRANGE__RESULT_RANGE_STATUS & 0x04`，**超时只打警告不重启测量**。一旦卡在一个不返回的测量里，后面所有调用都读到同一个死值。

#### 缓存 + 新鲜度

传感器任务独立跑（20Hz），**它自己负责让数据永远是新的**，工具和 Web 只读缓存：

```cpp
struct SensorSnapshot {
    int     distance_mm;
    int     status;        // 0=ok 1=out_of_range 2=no_target 3=i2c_error
    int64_t stamp_ms;
    int     baseline_mm;
    bool    blocked;
    bool    sensor_ok;
    int     fail_count;
};
```

**关键字段 `age_ms`**（返回时算 `now - stamp_ms`）：

- LLM 看到 `age_ms > 1000` 就该说「传感器没有数据」，而不是把 3 秒前的 147mm 当现在
- Web 页面可以把过期数据标红

#### 自愈机制

```
每次测量：
  超时（100ms 没 ready）→ 写 SYSTEM__INTERRUPT_CLEAR，重发 SYSRANGE__START
  连续 3 次超时 → 完整重新 init()（重写那 30 个私有寄存器）
  连续 20 次失败 → sensor_ok_ = false，打 ESP_LOGE，进降级
  之后每 5 秒重试一次 init()
```

`init()` 那 30 个寄存器就是给这种情况准备的——传感器内部状态机卡死时，只有重写寄存器能拉回来。

#### Web 接口

`GET /api/sensor`，注册方式照 `web_server.cc:58` 的 `httpd_uri_t`：

```json
{
  "distance_mm": 147,
  "status": "ok",
  "age_ms": 45,
  "baseline_mm": 147,
  "blocked": false,
  "sensor_ok": true,
  "fail_count": 0
}
```

页面一秒轮询一次，显示四行：

```
距离  147 mm   [正常]
基线  147 mm
状态  正常     · 数据 45ms 前
闸门  未触发
```

调试价值：一边推摇杆一边看距离怎么变，直接量出「走一米要几秒」「离墙多远该停」。这解决了「结合动作调时间」的需求。

#### 工具

```json
self.sensor.get_distance()
→ {"distance_mm": 147, "status": "ok", "age_ms": 45, "blocked": false}

self.sensor.calibrate()
→ {"baseline_mm": 147, "ok": true}
```

`get_distance` 的描述里写清楚：**`age_ms` 大于 1000 就告诉用户传感器没有数据，不要猜距离**。这样 LLM 不会编。

#### 工具名额核算

| 组 | 数量 |
|---|---|
| `self.motor.move` / `self.motor.emotion` | 2 |
| `self.network.get_ip` | 1 |
| `self.rgb_led.*` | 9 |
| 官方 common（get_device_status / set_volume / set_theme） | 3 |
| user-only（系统信息/重启/升级/屏幕快照等） | 7 |
| **小计** | **22** |
| 新增 `robot.start` / `robot.stop` / `sensor.get_distance` / `sensor.calibrate` | 4 |
| **合计** | **26**，服务端上限 32，余 6 |

```
I (7704868) Application: << % play_music...
```

`search_music` 和 `play_music` 跑在服务端，返回的音频以 opus 流下发，设备当普通 TTS 播。对它来说这和"说话"是同一个状态（`kDeviceStateSpeaking`），**它不知道自己在放音乐**。

#### 但歌名能拿到

服务端把工具调用和歌名当 `sentence_start` 的文本发下来了：

```
I (7704868) Application: << % play_music...
I (7704888) Application: << 《星光引航》

I (7774398) Application: << % play_music...
I (7774428) Application: << 《单车池塘》
I (7775118) Application: << 骑着单车路过池塘
```

规律很清楚：

1. `% play_music...` —— 工具调用标记（`% ` 前缀是所有工具调用共用的，`% self.motor.emotion` 也是这个格式）
2. 紧接着一条 `《歌名》`
3. 后面是歌词

#### 识别方式（实际实现）

`display.h` 的接口是 `SetMusicMode(bool on, const char* title, const char* lyric)`，两个字符串传 `nullptr` 表示这次不改那一行。

`application.cc` 的 `sentence_start` 分支按顺序判断：

```cpp
std::string t = text->valuestring;
ESP_LOGI(TAG, "<< %s", t.c_str());

if (t.rfind("% play_music", 0) == 0) {
    awaiting_music_title_ = true;
    Schedule([display]() { display->SetMusicMode(true, "", ""); });
    return;
}
if (awaiting_music_title_ && t.size() >= 6 && t.compare(0, 3, "《") == 0) {
    awaiting_music_title_ = false;
    size_t end = t.find("》");
    if (end != std::string::npos && end > 3) {
        std::string title = t.substr(3, end - 3);
        Schedule([display, title]() { display->SetMusicMode(true, title.c_str(), nullptr); });
        return;
    }
}
if (display->IsMusicMode()) {
    // % 开头的是工具调用回显（% self.motor.emotion 之类），不是歌词，直接丢
    if (!t.empty() && t[0] == '%') return;
    Schedule([display, t]() { display->SetMusicMode(true, nullptr, t.c_str()); });
    return;
}
// 都不是，走普通字幕 + 语气联动
```

**`awaiting_music_title_` 这个标志是必需的。** 第一版没有它，判据只是「文本以 `《` 开头」——结果服务端列歌单时说「这几首：《A》《B》」也会被当成歌名，界面就跳到音乐页去了。加标志之后只在 `% play_music` 之后的第一条生效。

**TTS 停止时退出**：`tts` 分支的 `stop` 里 `if (display_mode_ == kDisplayModeMusic) SetDisplayMode(display_mode_before_music_);` —— 回到进音乐之前那一屏，不是固定回眼睛。

#### 界面布局（实际三行）

```
┌────────────────────┐
│   《星光引航》       │  y=0，14px 普慧，居中，带书名号
│  骑着单车路过池塘     │  y=18，46px 高 = 3 行，居中
│  风从耳边穿过        │  LV_LABEL_LONG_WRAP 自动换行
│  天很蓝             │
└────────────────────┘
```

**没有「正在播放」这一行。** 最初加过，实测占了整个额头还显示不全（`LV_SYMBOL_AUDIO` 在字库里没字形），而「看见歌名是个人都知道在播放」。删掉之后歌名上移到 y=0。

#### 三个踩过的坑

**一、字库缺字不报错。** `font_puhui_basic_14_1` 是精简库，只收官方 UI 用的字。查了一遍：

```
「正」✅  「在」✅
「播」❌  「放」❌  「歌」❌  「名」❌  「词」❌  「曲」❌
```

编译不报、运行不报，就是画出一个方框然后什么都不显示。`main/CMakeLists.txt` 的 `BUILTIN_TEXT_FONT` 换成 `font_puhui_14_1`（220KB → 1.7MB，固件涨 258KB）才全。**这个改动影响整个固件的中文显示，不只音乐界面**，换完 `build_reconf.ps1` 重跑。

**二、`\x` 转义会吃掉后面紧邻的十六进制字符。** `std::string with_marks = "\xE3\x80\x8A";` 想写「《」，C++ 把 `\xE3` 后面紧邻的 `80` 也当十六进制吞了，落进字符串只有 `E3`，`80 8A` 丢了。LVGL 拿到半截 UTF-8，画出来是 `ü`。写中文一律用字面量 `"《"`。

**三、滚动动画要自己配。** 只设 `LV_LABEL_LONG_SCROLL_CIRCULAR` 不够，还得给 `lv_obj_set_style_anim` 一个 `lv_anim_t`，否则 LVGL 用默认参数，几乎不动。官方 `chat_message_label_` 的写法在 `oled_display.cc:287-300`，照抄即可。两个 label 的 `lv_anim_t` **必须各自独立 static**——`lv_obj_set_style_anim` 只存指针，共用会让后者覆盖前者。

#### UTF-8 的两个坑

`《` 是 3 字节（`E3 80 8A`），`》` 是 3 字节（`E3 80 8B`）。

- `t[0] == '《'` 对 `std::string` 不成立（`char` 有符号，取出来是负值），必须用 `t.compare(0, 3, "《") == 0`
- `substr` 的起点和长度都要按字节算：`t.substr(3, end - 3)`，不是 `substr(1, end - 1)`

#### 风险

**这是依赖服务端文本格式的 hack。** 官方哪天改了 `% play_music` 的写法、或者把歌名换成别的格式，识别会失效，界面退回普通字幕。不会崩、不会卡，只是这个功能没了。

真要做可靠的音乐界面，得自己在固件里实现音乐服务——那是另一个项目的工程量，这次不做。

| 子模式 | 要传感器 | 行为 |

#### 不是任务的

| 东西 | 类型 | 周期 | 说明 |
|---|---|---|---|
| `idle_timer_` | `esp_timer` 单次 | 60 秒，每次操作重置 | 超时进时钟场景（§3.6），回调里 `CanEnterSleepMode()` 一票否决 |

用 `esp_timer` 而不是 FreeRTOS task：跑在 esp_timer 任务上下文里，不占独立栈，回调只有三行。

#### 测距频率：方案 B 之后可以放开

v206 那个 87% 超时率是**总线争用**造成的，不是传感器坏了。它的 `VL6180X` TAG 打了 665 行，331 次超时、49 次成功读数；失败后立刻重试，每轮 3 次 × 510ms = 1.53 秒，85% 的时间在死等 I2C。同时 RoboEyes 正以 30fps 往同一块 panel 刷 1KB 帧，按 400kHz 算每帧 23ms——两个病一个根。

**方案 B 把传感器挪到 I2C1 独立总线之后，这条限制解除**，测距按 20Hz 跑。VL6180X 单次测量典型 20-30ms，50ms 周期来得及。

哪天要是改回共用 I2C0，就得退回「待机 2Hz / 模式激活 10Hz」再加脏区检测。

#### 帧率不动 30fps，改脏区检测

一开始想过把 RoboEyes 从 30fps 降到 15fps 省总线。**这个方向是错的**——降帧率眼睛会肉眼可见地顿，而且只把占用从 69% 砍到 34%，治标不治本。

查 `roboeyes_adapter.cc` 的 `FlushToPanel()`，根因在这儿：

```cpp
for (int p = 0; p < pages; ++p) {
    esp_lcd_panel_draw_bitmap(panel_, 0, y_start, width_, y_end, page_ptr);
}
```

**没有任何脏区检测**，每帧无条件刷满 8 页 1024 字节，哪怕眼睛一动没动。

改成逐页 `memcmp`：

```cpp
// roboeyes_adapter.h 新增
std::vector<uint8_t> last_raw_;
bool first_flush_ = true;
```

```cpp
// FlushToPanel 内，打包成页格式之后
int first_page = -1, last_page = -1;
for (int p = 0; p < limit; ++p) {
    const uint8_t* cur = buf + p * width_;
    if (first_flush_ || memcmp(cur, last_raw_.data() + p * width_, width_) != 0) {
        if (first_page < 0) first_page = p;
        last_page = p;
    }
}
if (first_page < 0) return;          // 整帧没变，一个字节都不发
memcpy(last_raw_.data(), buf, width_ * limit);
// 只刷 [first_page, last_page] 这段连续页
```

估算：眼睛静止 0 页、微动 1–2 页、眨眼 4–5 页，平均 2.7ms/帧 × 30fps ≈ **8% 占用**。比全屏 30fps 的 69% 低一个数量级，比全屏 15fps 的 34.5% 也低得多。**帧率保持 30，眼睛还更流畅。**

配合 §3.2 的区域切分，眼睛只剩 6 页而不是 8 页，占用再降 25%。

**`roboeyes_panel_task` 是理解整块动画的钥匙。** `RoboEyesAdapter::StartTimer(int fps)` 有两条分支：

```cpp
if (panel_ != nullptr) {
    // 有 panel：起一个独立 FreeRTOS 任务，循环调 Update()
    xTaskCreatePinnedToCore([](void* arg) {
        RoboEyesAdapter* self = static_cast<RoboEyesAdapter*>(arg);
        int delay_ms = 1000 / (self->max_fps_ > 0 ? self->max_fps_ : 15);
        while (self->panel_task_running_) {
            self->Update();
            vTaskDelay(pdMS_TO_TICKS(delay_ms));
        }
        vTaskDelete(nullptr);
    }, "roboeyes_panel_task", 4096, this, tskIDLE_PRIORITY + 1, &panel_task_, 0);
} else {
    update_timer_ = lv_timer_create(RoboEyesTimerCallback, interval_ms, this);
}
```

2.1.0 的调用是 `roboeyes_adapter_->Begin(content_left_, width(), height(), 30, panel_io_, panel_)`——**传了 panel**，所以走第一条。

这解答了一个看着矛盾的地方：`SetAnimatedEmotionMode(true)` 里明明调了 `lvgl_port_stop()` 把 LVGL 停了，动画凭什么还在动？答案就是它压根不靠 LVGL 的定时器，自己开了一个任务直接刷 panel。

**副作用**：`application.cc:362` 调 `display->UpdateAnimatedEmotion()` 其实是空转——`OledDisplay::UpdateAnimatedEmotion()`（`oled_display.cc:436`）是空实现，动画完全由那个 FreeRTOS 任务自驱。这条空调用留着不碍事，但别指望它。

**不新增常驻任务**这句要修正：RoboEyes 那个任务在动画模式下是常驻的，4 KB 栈，绑 core 0（跟 httpd 同核）。灯效和情绪联动都挂现有的定时源，不另起任务。

| `roboeyes_panel_task` 任务栈 | **4 KB** | `xTaskCreatePinnedToCore` 里写死的 4096 |

| 测距轮询任务栈 | 3 KB | 只在 follow / edge_patrol 时存在 |

| WS2812 像素缓冲（5 × 3 字节） | 15 B | |

**实测数据（2.2.4 干净编译）：**

```text
Memory Type Usage Summary
| Flash Code        | 1,830,832 |                    |
| Flash Data        |   674,316 |                    |
| DIRAM             |   151,615 | 44.36 | 190,145 remain | 341,760 total |
```

### 4.4 I2C 总线：卡顿的真正来源

日志里那 87% 的测距超时率，不是 VL6180X 坏了，是总线被屏幕吃光了。算一下：

```
OLED 一帧 = 128 × 64 / 8 = 1024 字节
I2C 400kHz，每字节 9 bit（含 ACK）= 9216 bit
一帧传输时间 = 9216 / 400000 ≈ 23 ms
RoboEyes 30fps → 每秒 690 ms 在传屏幕
→ 总线占用率 69%
```

**69% 的总线被屏幕占着，67ms 里只有 20ms 留给别的设备。** VL6180X 在这个间隙里要完成「写启动寄存器 → 轮询状态 → 读结果」三步，任何一步被屏幕的 23ms 传输打断，时序就崩。日志里 `Timeout waiting for measurement ready` 每 510ms 来一次、连续 3 次，就是这么来的。

两个方案。**已选 B**，A 留作回退路径：

#### 方案 A（备选）：共用一条总线，靠限速和互斥

不动接线，把争用压到可接受范围：

| 手段 | 效果 |
|---|---|
| RoboEyes 加**脏区检测**（§4.2） | 总线占从 69% 降到约 8%，帧率不变 |
| 眼睛区缩到 6 页（0–47），LVGL 只占 2 页（48–63） | 再降 25% |
| 测距待机 2Hz / 激活 10Hz | 单次测量摊到 100ms 窗口，够单页屏幕帧插进来 |
| 测距改**连续测量模式**（`SYSRANGE__START = 0x03`） | 传感器自己按 90ms 周期测，CPU 只读结果，不再反复写启动寄存器 |
| 超时 200ms 就重发 START，**不再傻等 3×510ms** | 单次失败成本从 1.53 秒降到 200ms |
| 连续失败 3 次 → **退避 2 秒** | 避免失败风暴把总线彻底锁死 |

ESP-IDF 的 `i2c_master_bus` 内部有互斥锁，两个任务同时访问不会撞车，但**会排队**——排队就意味着 ToF 可能等一个 23ms 的屏幕帧。方案 A 的核心不是"消除等待"，是"让等待不超过超时预算"。

#### 方案 B（已选定）：VL6180X 单独走 I2C1

ESP32-S3 有**两个独立的 I2C 控制器**。屏幕留在 I2C0（GPIO41/42），传感器挪到 I2C1：

```c
#define TOF_I2C_PORT    I2C_NUM_1
#define TOF_SDA_GPIO    1
#define TOF_SCL_GPIO    2
```

好处是彻底物理隔离——屏幕刷多快都不影响测距，测距也不再需要限速到 2Hz。

**代价：要重新焊接两根线。** 现在传感器的 SDA/SCL 焊在屏幕分线板上，得改成直接飞到主控的空闲脚。

引脚可用性核对（已占用的排除掉）：

| 已占用 | 用途 |
|---|---|
| 0 | BOOT 键 |
| 3 | 已弃用（strapping，qebabe 原设计，改成 21） |
| 4 / 5 / 6 | I2S 麦克风 WS/SCK/DIN |
| 7 / 15 / 16 | I2S 功放 DOUT/BCLK/LRCK |
| 12 / 13 / 14 / 21 | DRV8833 IN1-IN4 |
| 18 | LAMP（官方自带的单色灯，本硬件未接） |
| 38 | WS2812 |
| 39 / 40 | 音量 ± |
| 41 / 42 | I2C0（屏幕） |
| 47 | 触摸键 |
| 48 | 板载 LED |
| 43 / 44 | UART0（串口日志，别动） |

**空闲可用：1、2、8、9、10、11、17。** 都不是 strapping 脚。

**定用 `GPIO 1 = SDA1`、`GPIO 2 = SCL1`**，两个脚挨着，好走线。

**第一批就按方案 B 接线。** 代价是得把传感器的 SDA/SCL 从屏幕分线板上拆下来，改焊到主控的 GPIO 1/2。这一步不做，第 6 步的测距会被屏幕刷帧干扰，重演 v206 那个 87% 超时。

暂时不想动烙铁的话，可以先用方案 A 跑通「能读到距离」这条，再改线——两者只差 `config.h` 里两个宏。

分两批：**搬的**（有现成代码，风险低）和**写的**（要新写，风险高）。交错进行，每步都编译验证。

| 步 | 模块 | 类型 | 状态 | 验收 |
|---|---|---|---|---|

### 试过但放弃的三项

| 项 | 为什么放弃 |
|---|---|
| 眼睛 + 字幕分屏 | 实测黑屏闪烁。LVGL 根容器不透明，藏 `container_` 或字幕滚动都会触发整屏重绘，把上半屏的眼睛一起刷掉。真要做得自己接管 flush callback 只发 y≥48，改动面远大于收益，用户也判断「效果不太理想」 |
| 换唤醒词 | 手里那两个包是 **MN6 命令词引擎**，不是 wn9 唤醒词模型。`srmodels.bin` 里搜不到 `wn9`/`nihaoxiaozhi`，只有 `MN6_v3_chinese_8_0.9_0.90` 和 300 多条家电命令词。换过去代价是识别变差、功耗变高，还丢了原来那个唤醒词 |
| v206 case 5-13 逆向 | `objdump -b binary -m xtensa` 对裸二进制的 `l32r` 常量池解析不准，反汇编出的目标地址落在所有段之外。explore 用方向码 0-4 已经跑得挺好，不值得为几个夸张动作再啃 |

**每步之后都要 build。** 不批量搬，防止一次报几十个错分不清来源。

### 这一周冒出来的新结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | **`CONFIG_FREERTOS_HZ=100` 让 `pdMS_TO_TICKS(5)==0`** | 所有 `vTaskDelay(pdMS_TO_TICKS(n))` 在 n<10 时变成「立即返回不让出 CPU」。表现为 2000ms 的超时循环 10ms 就跑完、闪烁节奏完全不对、忙等疯狂读 I2C。必须用 `xTaskGetTickCount()` 计数 + `vTaskDelay(1)` |
| 2 | **`font_puhui_basic_14_1` 是精简字库，缺字不报错** | 「播放歌名词曲」九个字里只有「正在」有。换成 `font_puhui_14_1`（220KB → 1.7MB）才全。这件事没有任何编译期或运行期提示 |
| 3 | **`\x` 转义会吃掉后面紧邻的十六进制字符** | `"\xE3\x80\x8A"` 想写「《」，实际落进字符串只有 `E3`，`80 8A` 被当十六进制吞了。写中文一律用字面量 |
| 4 | **服务端可能不发 `tts stop`** | 表现为永远停在 `speaking`。兜底：`AudioService::IsIdle()` 之后 3 秒强制切回 `listening` |
| 5 | **观察动作会改变被观察对象** | pyserial 打开 COM3 会拉低 DTR/RTS，CH343 那两个脚接 GPIO0 和 EN，设备直接重启。想验证状态持续只能靠 HTTP 轮询 |
| 6 | **`max_uri_handlers` 不是 Kconfig** | IDF 5.5.4 压根没有 `CONFIG_HTTPD_MAX_URI_HANDLERS`，写进 sdkconfig 会被 `reconfigure` 抹掉。真实位置是 `httpd_config_t` 结构体字段，默认 8 |
| 7 | **`esptool ... run` 能软复位** | `--after hard_reset run` 会走 RTS 复位，不用再物理拔插 USB。之前「CH343 的 RTS 没接 EN」的结论是错的 |

目前没有卡住的东西。剩下的只有打磨：WS2812 的灯效细节。
